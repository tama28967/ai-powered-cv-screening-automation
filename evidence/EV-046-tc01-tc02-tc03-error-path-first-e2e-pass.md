**Reason:** With the Webhook intake serving (EV-045), this is the first time any PRJ-0001 workflow has executed end-to-end through its real deployed entry point. Four ordinary engineering defects were found and remediated by real execution — none were visible to static validation, because nothing had ever reached these code paths before.

**Defects found and remediated during this round's E2E runs (all TEST-only, all redeployed and re-verified):**
1. **Drive upload binary-field mismatch:** the Webhook node's multipart parser named the uploaded file's binary property `resume_pdf0` (index-suffixed), not the configured `resume_pdf`; `Upload to Google Drive`'s `inputDataFieldName` was a stale `data`. Fixed by setting it to the empirically observed `resume_pdf0`.
2. **executeWorkflow `workflowId` shape/typeVersion mismatch:** at `typeVersion: 1`, `n8n-nodes-base.executeWorkflow` reads `workflowId` as a raw parameter (expects a plain string); our nodes store it as the resourceLocator object `{__rl:true,...}` (correct per round 3's DEF-005 remediation, which fixed the *shape* but not the *typeVersion* needed to read that shape at runtime). Confirmed by reading the installed node's compiled source (`GenericFunctions.js`: `nodeVersion === 1` branch vs. the `else` branch that destructures `.value`). Fixed by bumping all 6 `executeWorkflow` nodes across MAIN, Extraction, AI Evaluation, and Duplicate Detection to `typeVersion: 1.1`.
3. **Duplicate-detection zero-item starvation:** `Lookup Existing Records by Email` returning 0 rows (correctly, no duplicate) left the `Duplicate Found?` IF node and everything downstream unexecuted, because n8n does not invoke a node — including an inserted Code node — when its input has zero items. Fixed with `alwaysOutputData: true` on the Lookup node (so an empty placeholder item always flows through) plus a `Determine Duplicate Status` Code node that distinguishes a genuine matched row (`m.json.record_id` present) from the empty placeholder, always emitting exactly one item with an explicit `duplicate_found` boolean; the IF condition was corrected to `boolean`/`equals`/`true`.
4. **Error Handling call-site data loss (4 call sites: MAIN, Extraction, AI Evaluation, Duplicate Detection):** the `executeWorkflow` `workflowInputs` resourceMapper (`mappingMode: "defineBelow"`) silently passed the caller's *entire* upstream item through instead of the explicitly mapped `{record_id, failure_mode}` object — confirmed by execution data showing the callee's trigger receiving the full upstream JSON, not the mapped fields. The Error Handling sub-workflow's own `Switch` node (`Route by Failure Mode`) also had all 4 rule conditions missing their `operator` field (same shape-defect class as round 4's DEF-006, unexercised until this round since nothing had ever reached Error Handling). Fixed by inserting a `Build Error Input` Code node at each of the 4 call sites (constructs `{record_id, failure_mode: "<literal>"}` explicitly), switching each `executeWorkflow` node to `mappingMode: "autoMapInputData"`, adding the missing `operator` fields to the Switch node, and declaring the Error Handling sub-workflow trigger's expected input fields (`record_id`, `failure_mode`) to match its siblings.
